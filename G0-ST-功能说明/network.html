6.1 蓝牙和 WiFi 怎么共用串口

只有一根 UART。程序不把时间切成固定时隙，而是保证同一时刻只有一条 AT 命令在等应答。

wifi_ble_task 先跑 bw20_handle，再跑 at_parser_process 消化串口字节。初始化完成后进入循环态，每次都先调用 wifi_tcp_handle，再调用 ble_handle。两边都通过 at_send_command 发命令。若 cmd_pending 已经为真，函数直接返回失败，状态机留在原状态，5 ms 后再试。收到 OK、ERROR、READY，或等待超时，才把占用清掉。

因为 WiFi 写在前面，同一拍两边都要发、且通道空闲时，这一拍归 WiFi。WiFi 发送是两拍：先 AT+SOCKETSEND，等到提示符 > 再发数据，直到 OK 才回到可发送状态。蓝牙回手机数据同样是 AT+BLESENDRAW 再等 >。这两拍期间占用不释放，另一边插不进来。

下行不占这条命令锁。解析器从同一段字节流里拆：蓝牙 +DATA 进 bt_rx_buf 再交给 BT_Task；socket 下行进 TCP 缓冲；+EVENT 更新连上、断开、拿到 IP。所以接收可以和一条正在等待的 AT 叠在一起，只有主动发命令才串行。

广播打开之后，蓝牙停在等连接，不再发 AT。只有 bt_tx_len > 0 才来抢命令槽。空闲时通道给 WiFi 做连路由、查 socket、发 OCPP。

6.2 WiFi 怎样把 OCPP 连上

  1. 未连上路由时，大约每 30 秒发一次 AT+WJAP。
  2. 已关联后等拿到网，或最多再等 25 秒，发 AT+WJAP? 读 IP。
  3. 读到 IP 后发 AT+SOCKET=3,502，打开本机 Modbus 端口。
  4. 读 AT+WRSSI。信号小于 0 且 OCPP 这条 TCP 还没连上，才发 AT+SOCKET=4,主机,端口。
  5. 应答里出现 connect success：tcp_connected[INTF_WIFI_ESP32] 置 1，状态进入可发送。从这一拍起，OCPP 的 net_check 才可能为真。

OCPP 组好的字节在 tcp_tx_buf。状态处于可发送且长度大于 0 时，才发 SOCKETSEND。通道被蓝牙或上一条命令占着时，数据留在缓冲里。

已连接后又 20 分钟没有 OCPP 收包，并且当前上网接口是 WiFi，BW20 发 AT+RST 复位模组。这不是清单里写的“空闲 60 分钟重启整机”。另外大约 3 分钟会查一次 socket 状态。旧 ESP32 初始化里有 AT+RESTORE，当前这条 BW20 路径复位用的是 AT+RST。

6.3 三种接口怎么选

重新配置时按使能位选择起点：开了局域网就用 W5500，否则开了 WiFi 就用 BW20，否则用 4G。地址以 wss 开头则这条连接走 TLS。

运行中 net_switch_process 按谁已经 TCP 连上做切换，不是按信号强度：

  • 正在用 4G，有线或 WiFi 连上了，就切过去，并断开 4G 这条。
  • 正在用 WiFi，有线连上了，就切到有线。
  • 有线或 WiFi 掉成“需要换路”时，先试 WiFi，再试 4G。

切换会复位对应连接，OCPP 要重新握手。蓝牙连上手机、而当前上网不是 WiFi 时，会暂时把 WiFi 串口中断优先级抬高，方便配置；蓝牙断开后再按当前上网接口把优先级放回 4G 或以太网。WiFi 模组升级进行到后半段、且当前接口是 WiFi 时，net_process 直接返回，避免和升级抢串口。

4G 状态机在 1 ms 的 SIM_Task。以太网在 5 ms 的 LAN_Manager，里面带网页服务。OCPP 字节只从 net_interface 指向的那一条出去。

7.4 链路连接和加密认证

要分开两层。手机和模组的 BLE 连接由 BW20 自己完成，桩只看到 +BLESTATE 把 bt_connected 置 1，以及 +DATA 里的字节。加密不在 BLE 配对里做，而在这些字节上的应用协议，入口是 BT_Task。

步骤谁先做什么
1. 空中连接手机连模组广播已在初始化里打开。连上之前桩不跑应用协议
2. 连接命令 0x21手机，明文帧头必须是 0xA5 0xA5，类型 0x01。未连接时别的命令直接回错误 0xE2
3. 协商密钥桩计算后明文回复见下面的密钥表。回复帧头是 0x5A 0x5A，协议版本字符是 '0'+7
4. 密码 0x23手机，已按协商模式加密8 字节密码对上才把 password_accept 置 1
5. 业务命令手机没通过密码时，只放行连接、退出、密码、读设备信息、读序列号、读充电状态
6. 退出 0x22手机清掉连接和密码标志，加密模式改回不加密。若改过参数，先 sys_param_set 再重启

帧

头 5 字节：起始 2、类型 1、命令 1、载荷长度 1。后面是载荷、1 字节累加和、结束字节 0x88。累加和在解密之前核对，所以加密帧核对的是密文。对不上分别回 0xE7 帧头、0xE1 类型、0xE3 长度、0xE6 无 0x88、0xE5 校验和。

密钥怎么出来

gen_key(序列号) 得到 2 字节客户码 cuscode 和 32 字节 cuskey。手机连接帧里带 2 字节 custom_code 和 8 字节随机数 A。桩自己再生成 8 字节随机数 B。

密钥算法用在哪
回复里的 key 字段SHA1(cuscode ‖ cuskey ‖ 随机数B) 的前 8 字节，再转成 16 个十六进制字符明文放进连接应答。应答发出去时还没换成下面的会话密钥
会话密钥SHA1(cuscode ‖ cuskey ‖ 随机数A ‖ 随机数B) 的前 16 字节应答组包之后立刻覆盖 app_sha1_key 和 charger_sha1_key。后面所有加解密都用这 16 字节

手机要自己用同一个序列号派生出 cuscode、cuskey，并用自己的随机数 A 和应答里的随机数 B 算出同一把会话密钥。桩不会把这 16 字节会话密钥原样发给手机。
