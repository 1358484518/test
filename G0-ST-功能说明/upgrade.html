升级

主控固件先下到外部 W25Q，写完标志后重启，由 Boot 去搬。这一份应用工程里没有 Boot 的搬运代码，应用只负责下载、校验、写标志，以及重启后根据 fw_update_state 上报结果。

平台发 UpdateFirmware 之后

RecvCall_OCPP_UpdateFirmware 先回 CallResult。若这时已经有一次升级在进行（fw_update_ctx.enable 已为 1），新的请求不再改 URL。

  • 地址以 WIFI-OTA-URL: 开头：不下载主控固件。把后面的 URL 交给 WiFi 模组升级，状态置 1，并记下开始时刻。
  • 其它地址：存进 fw_update_ctx.URL。能解析 retrieveDate 就等到那个时刻，解析失败就从现在开始。重试次数和间隔用平台给的值，使能位置 1，并标明这不是签名升级。

签名升级是另一条报文 SignedUpdateFirmware。已有升级在进行则回 Rejected。否则先验签名证书，通过后同样记下 URL、时间和证书、签名，置签名升级标志。清单写这项不支持，这条接收函数在源码里是接上的。

什么时候真正开始下

OCPP_Task 每次都调用 ocpp_update_firmware。它先看几件和下载无关、但和结果有关的事：

  • 当前上网接口是 WiFi，而这会儿 TCP 又不通：把下载状态清掉，直接返回。有线或 4G 不走这个判断。
  • sys_param.fw_update_state 若是 2，上报 Installed；是 3，上报 InstallationFailed。12 和 13 是签名升级对应的成功和失败，改发 SignedFirmwareStatusNotification。报完把这个字段清 0，并置保存标志。这几个值是重启之后才可能看到的，用来告诉平台 Boot 装没装上。

使能位为 0，或还没到开始时刻加 2 秒，不下载。桩处在准备、充电、暂停、结束，或者两条 OCPP 连接还有报文没发完，也不下载。也就是说必须空闲。

条件满足后：停掉心跳标志，状态改成 Downloading 并上报，把桩设为不可用（unavailable_enable = 1），先空等 400 次调用，再进 do_firmware_update。整段下载若超过 300 秒没有进展，按失败处理。

HTTP 下载和文件头

下载是一个掉电不保存的状态机，每进来一次只推进一步。

  1. 解析 URL 的主机、端口、路径。以 https 开头则打开 TLS，并先把第二路 OCPP 的 TLS 拆掉，避免两套 TLS 抢同一条网。同时置 fw_update 和串口过滤停止，避免 WiFi 串口解析把下载字节当 AT 应答。
  2. 连接服务器。大约每 200 次尝试连一次，超过约 600 次还不行就失败。
  3. 连上后灯改成红灯常亮，发 HTTP GET。头里带 Host、keep-alive，不要求压缩。
  4. 收满 1024 字节后找 HTTP/1.1 200、Content-Length 和空行。缺任何一项失败。整包长度必须在 10KB 到 512KB 之间。
  5. 空行后面是自定义文件头。头里的文件长度不能超过 512KB，也不能比 HTTP 长度还大。文件类型必须是主控类型，或者 9。类型 9 写到从机固件地址，其它类型写到 DEV_ROM_SPI_ADDR_BEG_DOWNLOAD。

正文按 1024 字节凑齐再写入外部 W25Q，同时累加 Modbus CRC16。签名升级还会对正文做 SHA256。写的时候红灯亮，写完灭，所以下载过程灯会闪。收满文件头里的长度后断开网络。

校验、写标志、重启

签名升级先用平台带来的证书和签名验 SHA256。验失败返回 -10，状态变成 DownloadFailed，不写标志。

验过之后比较文件头里的 CRC 和刚算出来的 CRC：

  • 一致：在外部 Flash 的文件信息区写入完成结构。标志 0x1234ABCD，长度用文件头里的长度，名字固定 App.bin，CRC 用头里的值。然后置延时重启。这次下载对应用来说成功，上报 Downloaded，fw_update_state 写成 1；签名升级写成 11。同时清掉不可用标志。
  • 不一致、但签名已经通过：不写主控完成标志，改成从机升级。置 update_master_or_slave = 1，从机状态置 1。函数仍返回 0，所以上层也会把它当成下载成功去上报 Downloaded。

失败时上报 DownloadFailed，重试次数加 1。还没到平台给的次数，就按间隔再等一轮；到了就关掉使能，并取消不可用。下载中桩被标成不可用，所以充电状态机会从等待进不可用，避免边充边写 Flash。

应用重启后不自己搬程序。Boot 看到 0x1234ABCD 才会从外部 Flash 把 App 拷进内部 Flash。拷完后若把 fw_update_state 写成 2 或 3（签名则是 12 或 13），应用下次起来会按上一节上报 Installed 或 InstallationFailed。

另外三条升级入口

网页

以太网 HTTP 的 /firmware.cgi 由 method_handle_update_page 处理。正文短于 10KB 直接返回。开头两个字节若是 0xFF 0xFF，先跳过 10 字节头。数据写到同一块下载区。收包过程中红灯闪，30 秒没有任何数据就放弃并取消不可用。收齐后用 Flash 里的内容再算一次 CRC，结果是 0xFFFF 视为失败。否则同样写入 0x1234ABCD、长度、CRC 和名字 App.bin，网页提示约 10 秒后重启，并置立即重启标志。

WiFi 模组自己的固件

不是主控 App。UpdateFirmware 的地址若带 WIFI-OTA-URL:，只把 URL 交给模组。BW20 任务看到升级状态后改发 AT+OTA。状态大于 1 且当前上网是 WiFi 时，net_process 不再做接口切换，避免和 AT 升级抢串口。

4G 模组

SIM_Task 在 4G 使能、并且 sim_ota_flag 为 1 时，要求桩处于等待、故障或不可用，OCPP 发送空闲，再延时约 2 秒，调用 quectel_fota。失败把标志写成 2，成功写成 3。

蓝牙

bt_cmd_fw_download 能把分包写入外部 Flash，收齐后也写 0x1234ABCD。但这三条命令在命令表里被注释掉了，正常蓝牙会话不会进到它们。清单写的“不支持、用 cptool”和当前启用的命令表一致；函数本体还留在文件里。
