# 充电桩收费系统总体方案

基于当前仓库中的 **STM32H573 + USART1** 桩端工程，规划一套可落地的充电桩收费系统。目标：从「能通信」演进到「能计费、能收款、能运营」。

---

## 1. 系统全景（四层）

```
┌─────────────────────────────────────────────────────────┐
│  用户层：小程序 / App / 刷卡 / VIN / 即插即充              │
├─────────────────────────────────────────────────────────┤
│  平台层：运营后台 + 计费引擎 + 支付 + 订单 + 对账           │
├─────────────────────────────────────────────────────────┤
│  接入层：OCPP/私有协议网关、设备鉴权、消息队列、断线缓存     │
├─────────────────────────────────────────────────────────┤
│  桩端层：STM32 控制器、电表、枪控、屏显、4G/以太网模组      │
└─────────────────────────────────────────────────────────┘
```

当前仓库只覆盖 **桩端层中的 MCU 串口基础**；收费系统的核心在平台层，但必须和桩端计量、启停、状态上报闭环。

---

## 2. 一次完整充电计费闭环

```
找桩 → 鉴权(预付/免密/会员) → 下发启动
  → 桩端开始充电并周期性上报电量(kWh)/功率/SOC
  → 停止(用户/满电/余额不足/故障)
  → 平台按电价策略结算 → 扣款/开票 → 订单归档 → 对账
```

**收费系统必须保证的三件事：**

1. **计量可信**：电量以合规电表读数为准，桩端 MCU 只做转发与本地保护，不可随意改写度数。
2. **订单幂等**：同一枪、同一会话只能生成一笔主订单；断线重传不能重复扣款。
3. **钱账一致**：预授权/预付余额、实扣金额、退款、分账可追溯。

## 3. 推荐技术架构

| 模块 | 建议选型 | 说明 |
|------|----------|------|
| 桩端 MCU | STM32H573（现有） | 负责枪控、与电表/屏/通信模组交互 |
| 桩 ↔ 云 | OCPP 1.6J / 2.0.1，或自研 JSON over MQTT | 国内很多运营商用私有协议；若要接第三方平台优先 OCPP |
| 通信链路 | 4G Cat.1 / 以太网 → MQTT/WebSocket | USART1 可接 4G 模组或外置网关 |
| 云接入 | 设备网关 + Kafka/RabbitMQ | 削峰、断线补传、按站点分流 |
| 业务服务 | Go / Java / Node（任一）微服务或单体起步 | 早期单体即可：设备、订单、计费、支付 |
| 数据库 | PostgreSQL + Redis | 订单/账务用 PG；会话状态、费率缓存用 Redis |
| 支付 | 微信/支付宝商户 + 预付钱包 | C 端先做「余额预付 + 结束后结算」最稳 |
| 运营后台 | Web（React/Vue） | 站点、费率、对账、客服退款 |
| 用户端 | 微信小程序优先 | 扫码启停成本最低 |

### 3.1 与现有 USART1 工程的衔接

当前 `usart1` 工程已打通 **PA9/PA10 USART1**。后续桩端建议分层：

```
应用层：充电状态机、计费会话、本地费率缓存、故障保护
协议层：OCPP/私有帧编解码、CRC、重传、心跳
驱动层：USART(电表/4G/屏)、GPIO(枪锁/继电器)、ADC/CAN(按硬件)
```

USART1 典型用途（按硬件选型二选一或扩展多路 UART）：

- 接 **4G/Wi‑Fi 模组**：MCU 通过 AT/透传把会话上报云端
- 接 **智能电表**：读取累计电量作为计费依据
- 接 **屏/读卡器**：本地人机交互

## 4. 计费引擎设计（收费核心）

### 4.1 费率模型

支持组合计价，避免写死「一度电多少钱」：

- **分时电价**：尖/峰/平/谷（按站点时区切段）
- **服务费**：按 kWh 或按分钟
- **占位费**：充满后未拔枪超时计费（可选）
- **会员折扣 / 优惠券 / 活动价**
- **最低消费 / 封顶价**（运营策略）

结算公式示例：

```
应付 = Σ(分段电量 × 分段电价) + 服务费 + 占位费 − 优惠
实扣 = min(应付, 预付/预授权可用额度)
```

### 4.2 关键核心表（最小集）

- `stations` / `chargers` / `connectors`：站、桩、枪
- `tariffs` / `tariff_periods`：费率与分时
- `users` / `wallets` / `wallet_ledger`：用户与资金流水
- `charging_sessions`：一次充电会话（设备侧 session_id）
- `orders`：订单（金额、状态、支付单号）
- `meter_values`：电量采样点（用于争议与审计）
- `payments` / `refunds`：支付与退款

### 4.3 会话状态机

```
Created → Authorized → Charging → Stopping → Settled
                              ↘ Faulted → Settled/Closed
断线：Charging 保持，补传 meter；超时未结束走强制结算策略
```

## 5. 支付与风控（务必先想清楚）

**推荐起步模式：预付余额 / 预授权**

1. 用户充值或扫码预付 N 元  
2. 云端校验余额 ≥ 站点最低门槛后才下发 `RemoteStart`  
3. 充电中按阈值刷新预估费用；余额不足则 `RemoteStop`  
4. 结束后按真实电量结算，多余退回钱包  

**不推荐一开始就「先充后付免密」**：坏账与纠纷成本高。

风控要点：

- 设备证书/密钥鉴权，拒绝伪造桩  
- 电表跳变、回退检测  
- 订单金额异常阈值告警  
- 所有扣款/退款写不可篡改流水

## 6. 分阶段实施路径

### 阶段 A：桩端能控、能量（当前 → 近期）

- 完善 STM32：枪插入检测、启停继电器、急停、状态机  
- 电表通信（Modbus/厂家协议）拿到累计 kWh  
- USART 接到通信模组，打通「心跳 + 启停 + 电量上报」最小协议  
- 云端用一个简单 MQTT 订阅服务落库（可先无服务器脚本）

**验收**：人工在后台点「启动/停止」，能看到实时电量。

### 阶段 B：能计费（MVP 收费）

- 实现会话、订单、分时费率、预付钱包  
- 小程序：扫码 → 支付/扣余额 → 启动 → 结束看账单  
- 运营后台：站点、费率、订单查询、手动退款  

**验收**：真实或模拟桩跑通「扫码充电并扣款」。

### 阶段 C：能运营

- 对账（支付渠道 ↔ 订单 ↔ 电量）  
- 发票、分账（物业/投资方）  
- 占位费、会员、优惠券  
- 监控告警、远程升级（FOTA）  
- 若需要互联互通，再切/兼 OCPP 或中电联协议  

### 阶段 D：规模化

- 多租户运营商、白标 App  
- 即插即充（PnC / 车牌/VIN）  
- 大数据：负荷预测、动态电价

## 8. 最小可行协议字段（私有协议起步）

若暂不上 OCPP，建议先定 JSON 帧（经 MQTT）：

**桩 → 云**

- `heartbeat`：桩 ID、枪状态、网络、故障码  
- `meter`：session_id、累计 kWh、功率、电压、电流、时间戳  
- `event`：插枪/拔枪/启动成功/停止原因  

**云 → 桩**

- `remote_start`：session_id、用户标识、最大可充电量或金额上限  
- `remote_stop`：session_id、原因  
- `config`：心跳间隔、上报周期、费率摘要（可选本地显示）

每帧带：`msg_id`、`ts`、签名/HMAC，云端按 `msg_id` 去重。

## 9. 合规与工程注意

- 计费用电表需满足当地计量要求；宣传「一度多少钱」要以表计为准  
- 支付涉及资金：商户号、分账、退款时效、客服工单要同步设计  
- 个人信息（手机号、车牌、定位）做好脱敏与权限  
- 断电/断网策略：本地可继续充到安全阈值，恢复后补传再结算

## 10. 下一步立刻可做的 3 件事

1. **定产品边界**：先做「单站 + 小程序预付 + 后台订单」，还是一上来要对接某运营商平台。  
2. **定桩云协议**：私有 MQTT JSON（快）还是 OCPP（易互联）。  
3. **在 `usart1` 上扩展**：第二路串口接电表或 4G，实现心跳与电量上报样例。

如果你确定协议选型（私有 MQTT / OCPP）和第一期范围（只做后端 / 含小程序 / 含桩端状态机），可以在本仓库直接开第一期工程骨架。
