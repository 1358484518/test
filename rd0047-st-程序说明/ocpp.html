OCPP

桩用 OCPP 1.6 的 JSON 报文跟平台说话，外面套一层 WebSocket。可以同时有两路：OCPP_NET 是运营平台，订单、刷卡授权、充电计划都走这一路。OCPP2_NET 是管理平台，只在管理平台打开时才连，只报状态、心跳、固件和诊断，不发开始交易、结束交易和电量。同一路同一时刻只发一条，等平台回了再发下一条。WebSocket 握完手先发 BootNotification。

什么时候发哪一类

WebSocket 已连通先发 BootNotification。这一条没发出去之前，不排别的
平台接受，并可能改心跳间隔。间隔小于 20 秒不采用
运营平台在线状态变化发 StatusNotification。一进准备就发一次 StartTransaction，进充电不再发。结束发 StopTransaction。充电和暂停才发 MeterValues
网断了，或发出去的订单没收到应答
先写进外部 Flash进准备写一条开始，充电和暂停按间隔写电量，进入结束写一条结束。充电本身不停
重新 Boot 被接受，队列里还有纸条
按写下的顺序补发Boot 被接受后，先发最早的一条。平台回了才发下一条。发完才恢复进准备就直接发

运营平台空闲时的发送顺序是：Boot、0 号连接器状态、1 号连接器状态、心跳、DataTransfer、Authorize、固件状态、签名固件状态、诊断状态、安全事件。这些都没有时，如果正在补传离线记录，就按记录里的类型发开始、结束或电量。没有离线记录才发当前的 StartTransaction、StopTransaction、MeterValues。管理平台没有 0 号连接器状态，也没有 Authorize、订单和签名固件状态。

安装测试模式里，MeterValues 的发送标志仍会被置上，真正发出前被丢掉，平台收不到这条。触发报文的应答仍然可以是 Accepted。

桩主动发的每一条

BootNotification

告诉平台这台桩是谁。WebSocket 一连通就发。填厂商 charge_point_vendor、型号 charge_point_model、桩号 chargerID 放在 chargePointSerialNumber、序列号 sn 放在 chargeBoxSerialNumber、固件版本 ApplicationVersion。当前这条连接走 4G 时再带 ICCID 和 IMSI。

平台接受后，这一路记下已注册，用平台给的时间对时并保存。心跳间隔不小于 20 秒、并且通过间隔检查，才改本地值。运营平台改的是 sys_param.ocpp_HeartbeatInterval，管理平台只改内存里的 ocpp2_HeartbeatInterval。同时把 StatusNotification 标志置 1，网络状态写成已登录。运营平台还会记下首次连上的时刻。不接受就按平台给的间隔再试，已注册标志清 0。间隔为 0 时不改重试时间。

Authorize

只在运营平台发。里面只有 idTag，就是当前 charge_handle.idTag。平台回 Accepted，桩把 on_charging 置 1。其它结果把授权清 0，停止原因是 DeAuthorized。结果同时写进授权缓存。

StatusNotification

枪状态或故障码变了就发。0 号连接器只用 chargestate0，报整桩是否可用、故障或不可用，这一条只有运营平台发。1 号连接器报等待、准备、充电、暂停、结束、预约。心跳间隔配成 0 或大于 3600 秒时，1 号枪状态还会每小时再报一次。管理平台用运营平台的心跳间隔做这个判断。

没有故障时 errorCode 是 NoError。接触器拒动或粘连是 PowerSwitchFailure，info 分别写 Contactor Fault 和 Contactor Welded。过压、欠压的 info 是三相电压原值，中间用空格分开。过流是 OverCurrentFailure。接地失败是 GroundFailure，info 写 L-N 和 L-PE。过温是 HighTemperature。电表超时是 PowerMeterFailure：MID 和 DLM 计数都大于 20 写两个都坏，否则写坏的那一个。其余用 OtherError，并带上厂商名。vendorErrorCode 按故障位写成 RCM selftest failed、RCD leakage、PE leakage、CP abnormal、Emergency stop、TamperDetectionActivated。对不上的写 Unknown，info 里带故障号。

平台回了这条之后，桩把这一路的 Boot 已接受标志再写一次 1，网络状态写成已登录。应答内容本身不再往下处理。

Heartbeat

按心跳间隔发，报文体是空的。平台回应当前时间，桩用来对时。

StartTransaction

一笔订单只发一次，发在准备，不发在充电。等待里已经授权、并且枪已经插上，CHARGE_STATE 才从等待改成准备。OCPP 看到准备、并且 is_transaction_start 还是 0，就把这个标志写成 1，排上 StartTransaction。之后进入充电，接触器吸合，标志已经是 1，不会再发。充电和暂停也写在判断里，只是兜底：如果准备阶段没记上，第一次看到充电或暂停仍会补发这一次。

只插枪、还没授权时，OCPP 状态可以显示 Preparing，但内部状态仍是等待，不发 StartTransaction。只授权、还没插枪，也停在等待，超时后授权被清掉，同样不发。

只在运营平台、并且当前没有离线记录要补时才真正发出。connectorId 固定 1。idTag 是当前授权卡号。meterStart 是 charge_handle.meter_start，单位 Wh。有预约号就带上，带完把本地预约号清 0。时间戳是当前时间，格式 YYYY-MM-DDTHH:MM:SS.mmmZ。发出时把 transactionId 写成 -1，等应答里的正式号。

离线补传时，连接器、卡号、起点电量、预约号和时间都改从本地开始记录里取。

应答如果正在补传，桩记下平台给的事务号，丢掉这一条本地记录，不再看授权结果。正常订单里，模式 1 会把应答里的 idTagInfo 写入授权缓存。授权是 Accepted，或者充电模式不是 1，这笔继续，invalid_ID 清 0。模式是 1 且不是 Accepted，把 on_charging 清 0，停止原因 DeAuthorized。代码里还有 auth_type 为 1 或 2 的分支，当前工程没有给它赋 1 或 2 的地方。光伏模式是 1 时，这条应答之后再排一条 DataTransfer，内容是光伏开始。

StopTransaction

运营平台且 Boot 已接受时，进入结束态就发。transactionId 是平台之前给的号。meterStop 是 charge_handle.meter_stop。reason 来自 stop_reason，并且带上这个字段。离线补传改用记录里的电量、原因和时间；卡号非空才带 idTag。软复位或硬复位如果在等这条发完，发出后把对应标志清掉，复位才能继续。

补传中的应答只丢掉这一条本地记录。正常应答里，模式 1 且带了 idTagInfo，就更新授权缓存。光伏模式是 1 时，再排一条 DataTransfer，内容是光伏停止。

MeterValues

充电或暂停中，采样间隔大于 0 就发。进入这个状态的第一次立刻发，然后按间隔重复。暂停里计数加 1，离开暂停再清 0。connectorId 是 1。准备、充电、暂停时带 transactionId。采哪些量由 MeterValuesSampledData 的开关决定。除了承诺电流的 context 是 Other，其余是 Sample.Periodic。

DataTransfer（桩发给平台）

发送函数一进来就看连接。管理平台直接返回，这条发不出去。运营平台的 vendorId 用厂商标识。messageId 由 DataTransfer_type 决定：

  • 1，DEBUG_EVENT：data 是调试事件字符串，发完类型清 0。
  • 2，GetCTClampValue：单相 data 是 current 和 voltage。三相是 L1 到 L3 的 Current 和 Voltage。电流是采样值乘 10，电压是 0.1 V 的数再乘 100。ocpp_GetCTClampValue 等于 2 时，这条发完把类型改成 3，平台一应答就再发下一条光伏钳位。其它值发完类型清 0。
  • 3，GetSolarClampValue：光伏电流乘 10，L1 电压乘 100。
  • 4，先看三个标志。开始标志发 SolarIndicator，solar 字段是 started。电量标志发 SolarMeterValue。停止标志再发 SolarIndicator，solar 字段是 stopped。三个标志都清掉之后类型才清 0。

SolarIndicator 带 connectorId 1、transactionId、solarEnergy 和时间。SolarMeterValue 带光伏电量 Wh、光伏功率 W、光伏允许电流 A，以及各相光伏电流。三相这串 JSON 在 L1、L2、L3 三条采样之间没有逗号。

DiagnosticsStatusNotification

日志上传过程中发。status 就是 log_upload_ctx.state。两路平台的发送标志都会被置上。应答只清超时计数。

FirmwareStatusNotification

主控升级过程中发。status 取 fw_update_ctx.state。平台应答时，如果当前状态是 Downloaded，桩把它改成 Installing，并再排一条固件状态。

SignedFirmwareStatusNotification

只排在运营平台。status 同样来自升级状态。结构里写了 firmware_requestId，但 requestId_exist 被写成 0，报文里不带这个号。应答时如果状态是 Downloaded，改成 Installing 再发一条。

SecurityEventNotification

安全事件。type 按事件号填：1 是 TamperDetectionActivated，2 是 InvalidFirmwareSigningCertificate，3 是 InvalidFirmwareSignature。其它号写成一个空格。时间戳到秒，没有毫秒。两路都会发。

平台下发的每一条

JSON 解不开时回 CallError，错误码按当时的 OCPP_ErrCode。下面是格式正确之后桩怎么处理。不认识的 Call 走 CallError，错误码 NotImplemented。

RemoteStartTransaction

默认拒绝。只有充电模式是 1，并且来自运营平台，才继续看。已经在充电且卡号不同，拒绝。没带连接器号就当成 1，连接器不是 0 或 1 拒绝。状态必须是等待、预约、准备或结束。预约中卡号不同，拒绝。带了充电计划时，用途必须是 TxProfile，并且本地 TxProfile 条数还没到上限。通过后这条计划写进 tx_profile 的第 0 条，条数改成 1，原来的 TxProfile 被盖掉。然后把 idTag 抄到 charge_handle，on_charging 置 1，蜂鸣一声，回 Accepted。

RemoteStopTransaction

默认拒绝。模式 1 且来自运营平台：还在充电，并且事务号等于当前 transactionId，才接受。模式 3 且来自运营平台：只要还在充电就接受，不看事务号。接受后蜂鸣一声，授权清 0，原因 Remote，full_stop 清 0。模式 2 和管理平台都拒绝。

UnlockConnector

连接器是 0 或 1，并且 pp_charge_enable 为 1，也就是枪线产品，才接受。置远程解锁，蜂鸣一声，授权清 0，原因 UnlockCommand，full_stop 清 0，状态回 Unlocked。枪座回 NotSupported。

ReserveNow

只处理运营平台，其它连接保持 Rejected。已经有预约则 Occupied。不是等待则 Rejected。不可用则 Unavailable。后面还有一条故障回 Faulted，但它排在「不是等待就拒绝」之后，等待态不会是故障，所以 Faulted 走不到。等待中、模式不是 2、还没授权、到期时间格式正确、连接器是 0 或 1，才接受：记下 idTag、预约号和到期时间，reserved_enable 置 1。同一条预约号在已经是预约态时也能再写，但前面的 Occupied 会先拦住已有预约，所以这条更新路径同样走不到。

CancelReservation

只在运营平台、当前是预约、并且预约号相同才接受，清掉预约标志和预约号。否则拒绝。

ChangeAvailability

连接器 0 或 1：Inoperative 把 unavailable_enable 置 1，ocpp_availability 写成 0。Operative 反过来。然后立刻 sys_param_set。正在充电、暂停或结束时回 Scheduled，其它情况回 Accepted。连接器号超出 0 和 1 则拒绝，参数不改。

Reset

硬复位和软复位都接受。类型不是这两种则拒绝。正在充电时先把授权清 0，停止原因分别是 Reboot 和 SoftReset，并置正常复位标志，好让 StopTransaction 先发出去。两种复位都会置延时重启。接受之后，如果之前改过运营平台地址、管理平台地址或上网接口，这时才写入参数。运营地址和管理地址相同，或者运营地址命中白名单，会把管理平台模式关掉，否则打开。白名单看地址里有没有 bgchprod、sync.energy、bgchtest、syncev。

GetConfiguration

不带键名时，回固定的一组，注释写明 configurationKey 最多 27 项。这一组里只读的有：AuthorizeRemoteTxRequests 固定 False，GetConfigurationMaxKeys，StopTransactionOnEVSideDisconnect 固定 true，StopTransactionOnInvalidId，SupportedFeatureProfiles，本地名单长度，发送名单长度，充电计划堆叠上限、时段上限、已安装计划上限，OEM_RSSI。可读可写的有心跳、连接超时、本地离线授权、采样量、采样间隔、入户电流间隔、拔枪解锁、本地名单开关、额定电流、充电模式、钳位上报、过压门限、上网接口、管理平台开关、DLB 模式、家庭电流上限。充电模式在这里只回 1 或 2：chargemode 不是 1 就回 2，模式 3 读出来也是 2。SupportedFeatureProfiles 的值是 Core、FirmwareManagement、LocalAuthListManagement、Reservation、SmartCharging、RemoteTrigger。

带了键名就按名字逐个回。一次最多 GetConfigurationMaxKeys 个，多出来的被截掉。不认识的名字放进 unknownKey。点名才能问到、空请求里没有的，包括 WebSocket 心跳、钳位间隔、CT 广播间隔、允许的计划单位 Current 和 Power、枪数、文件传输协议 HTTP、对齐采样三项空字符串、ResetRetries 固定 3、交易重发次数 3、重发间隔 15 秒、时钟对齐间隔 0、本地预授权、授权缓存、未知卡离线交易、无效卡电量上限、相序、灯光、桩号、欠压门限、时区、温度上限、光伏三项、即插即充指示、防拆、家庭负载开关和采样方式、电表地址、WiFi、4G、DHCP、静态地址、平台地址和密钥、管理平台地址和密码、累计电量、读卡供电、板载灯。

ClearCache

格式正确就接受，调用 auth_cache_clear 把授权缓存清掉。

GetLocalListVersion

格式正确就回 local_list_version()。

SendLocalList

先设成 Failed。版本号小于 1，或者差分更新的版本不比本地新，回 VersionMismatch。名单条数超过 SendLocalListMaxLength 保持 Failed。local_list_update 返回 0 才改成 Accepted。运营平台把请求原文和结果写进日志。

SetChargingProfile

先设成 Rejected。连接器不是 0 或 1，拒绝。stackLevel 大于等于 ChargeProfileMaxStackLevel，回 NotSupported。ChargePointMaxProfile 的连接器不是 0，拒绝。TxProfile 必须当前在准备、充电或暂停，并且事务号等于正在进行的 transactionId。同一条 TxProfile 里，计划号相同，或者堆叠级相同，就覆盖那一条。否则追加，条数到上限就拒绝。TxProfile 只留在内存。整桩上限和默认计划写进 max_txdefault_profile，同样按计划号，或按「堆叠级加用途」覆盖，然后写入外部闪存。运营平台把请求和结果写进日志。

ClearChargingProfile

带了连接器号、但不是 0 或 1，回 Unknown。三个条件都没带，删掉全部计划，回 Accepted。只带 id，按 id 删。只带用途，按用途删。只带堆叠级，按堆叠级删。用途和堆叠级都带，按两个一起删。删到了就 Accepted 并写外部闪存，没删到回 Unknown。

GetCompositeSchedule

先设成 Accepted。连接器大于 1 或小于 0 改成 Rejected。否则调用 sc_calc_schedule 填合成计划，并在应答里带回连接器号。

TriggerMessage

默认拒绝。BootNotification 和 Heartbeat 接受，并把对应发送标志置 1。MeterValues 和 StatusNotification 只在连接器是 0 或 1 时接受，同样只置标志。别的请求类型保持拒绝。真正发出要等当前没有在等应答。MeterValues 即使这里 Accepted，安装测试模式在发出前仍会丢掉。运营平台把请求和结果写进日志。

GetDiagnostics

先记下上传地址。带了开始或结束时间就解析，格式不对时开始时间用 0、结束时间用现在。没带也是这个默认。结束早于开始、结束早于本地日志起点、或开始晚于本地日志终点，应答里不带文件名，上传也不启动。时间有重叠时，把范围裁到本地日志的起止之内，记下重试次数和间隔，enable 置 1。文件名是 log-桩号-开始-结束.txt。随后在桩空闲时上传，过程用 DiagnosticsStatusNotification 报告。

UpdateFirmware

已经有一次主控升级在进行，这条请求被忽略，应答仍按空的确认发出。没有在升级时，地点以 WIFI-OTA-URL: 开头，是给 ESP32 模组升级，把后面的地址放进 wifi_fw_url，并记下开始时刻。否则是主控固件，记下 URL、重试次数和间隔。retrieveDate 能解析就用那个时刻，否则用现在。enable 置 1，并标明这次不是签名升级。

SignedUpdateFirmware

已经有升级在进行，回 Rejected，并清掉签名升级标志。否则先校验签名证书。证书不过回 InvalidCertificate。通过后记下 URL、时间、重试、requestId、证书和签名，enable 置 1，签名升级标志置 1，回 Accepted。

DataTransfer（平台发给桩）

没有 messageId，或者 messageId 不认识，回 UnknownMessageId。认识的三个：

  • GetCTClampValue：回 Accepted。data 只有一相，{"current":入户电流乘10,"voltage":L1电压乘100}。桩自己上报的那条才会分三相，这里不分。
  • 4GAT：把 data 当成 4G 模组的 AT 命令，等 OK，超时 1 秒。成功回 Accepted 和模组应答。失败把 data 清空，回 Rejected。
  • WIFIAT：同样把 data 发给 WiFi 模组，成功和失败的规则与 4GAT 相同。

断网时订单怎么补

充电照常进行。断网只是运营平台暂时收不到这三句话：开始、中间的电量、结束。桩把它们按发生顺序写进外部 Flash。网回来并且 BootNotification 被接受之后，从最早的一条开始补发。平台回一条，再发下一条。

网从插枪起就不通

WebSocket 没握上手时，OCPP_Task 不跟平台说话，改跑 ocpp_offline_store。下面是同一次充电：

桩这边写进 Flash 的一条
已授权并且插枪，状态变成准备开始。卡号、起点电量 meter_start、当时的时间。有预约号就记下，本地预约号清掉。充电阶段不会再写第二条开始
进入充电或暂停，并且采样间隔大于 0电量。当时的累计电量、功率除以 10、承诺电流、各相电压电流。隔 MeterValueSampleInterval 秒再写一条
进入结束结束。结束电量 meter_stop、停止原因、当时的时间。这条不写卡号

队列里的条数达到「一天能记的电量条数再加 48」之后，电量改成一小时写一条。开始和结束仍是各一条。

网通了以后怎么发出去

写进 Flash 的当时不发送。运营平台 WebSocket 连上之后，OCPP_Core_Handle 每次先调用 ocpp_check_message_triggle 决定下一条发什么，再调用 ocpp_local_send_call_message 组包。

BootNotification 刚被接受时，ocpp_check_message_triggle 调用 transaction_record_number。条数是 0，offline_transaction_exist 清 0，之后进准备就直接把 CurrentSendMsg 设成 StartTransaction。条数不是 0，这个标志置 1，进入补发。

补发时同一函数读队列最前面一条的类型，并设置 CurrentSendMsg：类型 1 是 StartTransaction，类型 3 是 MeterValues，类型 2 是 StopTransaction。Boot、状态、心跳、DataTransfer、Authorize、固件、诊断、安全事件这些还占着发送位时，要等它们发完，当前没有在等应答，才轮到这条离线记录。

下一拍 ocpp_local_send_call_message 按 CurrentSendMsg 调用对应的 Call_OCPP_*。因为 offline_transaction_exist 是 1，报文里的时间、电量、原因从 transaction_record_get 读出的那条记录来，不用眼前的充电状态。组完 JSON 后 Send_SameCode 发出去，并把 CurrentSendMsg 改成等待应答。

平台应答到来，开始、电量、结束三个接收函数看见仍在补发，就调用 transaction_record_dec，读指针加 1，这条算发完。StartTransaction 的应答即使 JSON 解不开，补发中也会丢掉这一条。队列里读到的类型对不上，offline_transaction_exist 清 0，才恢复进准备直接发。

补发还没完，又来一笔新充电，新的开始、电量和结束也写到队列末尾，排在旧记录后面。平台在 StartTransaction 应答里给的事务号由 transactionId_store 单独写在 Flash。后面的 StopTransaction 用 transactionId_init 读回的这个号。开始那条一直没得到应答时，结束报文里的事务号就还是 Flash 里的旧值。

话发出去了，平台没回

StartTransaction、MeterValues 或 StopTransaction 已经发出，超时次数到 3，或者网络检查失败。当时还没在补发的话，把这条没收到应答的按同样格式写进 Flash，然后断开。已经在补发时不再写，避免同一条记两次。重连并且 Boot 被接受后，从这条开始按上面的顺序补发。

能存多少条，存在哪

离线的开始、电量、结束存在外部 SPI Flash 的 0x003E0000 到 0x00400000，一共 128 KB。前面两扇区不放报文：0x003E0000 这一扇区记魔术字和读写指针，指针日志写满就擦掉重写最新的一对；0x003E1000 这一扇区只放事务号。真正的报文从 0x003E2000 起，到 0x00400000 止，30 个 4 KB 扇区。

每一格固定 38 字节，一扇区 4096÷38 得到 107 格，30 扇区一共 TR_MAX_NUM 等于 3210 条。开始记录本身就是 38 字节，结束是 34 字节，电量是 30 字节，地址仍按 38 字节往后排。写指针走到 3210 就回到 0 继续写，代码里没有“满了就不再记”的判断，新的一条会盖住被绕回去的那一格。

电量还有一个变慢的门槛，只在 WebSocket 没连上时使用。队列条数还小于 86400 / 采样间隔 + 48 时，按 MeterValueSampleInterval 写。到了这个数就改成一小时一条。默认间隔 60 秒时，门槛是 1488 条，比 3210 先到。开始和结束不受这个门槛限制，该写还是写。采样间隔配成 0 时不写电量。

充电中整机断电

进入充电时 charge_preparing 把 is_charging 写成 1，并调用 transaction_flag_store 写到外部 Flash。从暂停回到充电时，如果这个标志还是 0，会再写一次。正常走到结束，check_stop_charge_condition 返回 0，就把标志写成 0 再存一次。中途掉电走不到这次清零，Flash 里一直留着 1。

下次上电，main 调用 DEV_Init。它先 transaction_energy_init_V2 把累计电量读回来，再 offline_init，里面的 transaction_flag_init 从 Flash 读 is_charging。仍是 1 时，停止原因写成 Reason_PowerLoss，调用 transaction_stop_store(0)。参数 0 表示电量用 charge_data.energy，类型是结束。卡号那一行是注释掉的，所以这条没有 idTag。写完把 is_charging 清 0，再 transaction_flag_store。开机这一步只追加记录，不发送。

发送要等运营平台连上。BootNotification 被接受且队列不是空的，offline_transaction_exist 置 1。ocpp_check_message_triggle 读到队头类型是 TR_TYPE_STOP，把 CurrentSendMsg 设成 StopTransaction。队列里如果还有更早的开始或电量，那些先发，这条掉电结束排在后面。状态、心跳这些发送位空出来之后，ocpp_local_send_call_message 调用 Call_OCPP_StopTransaction。它从这条记录取出时间、meterStop 和原因 PowerLoss，事务号用 transactionId_init 读回的旧号，idTag 为空所以报文不带卡号，然后 Send_SameCode 发出去。平台应答后 RecvCall_OCPP_StopTransaction 调用 transaction_record_dec，把这条从队列去掉。

离线多久之后允许自己开始充

OfflineChargingTime 不管上面的队列。Boot 没被接受后再过这么多分钟，枪还插着、还没授权、状态是等待，就把 on_charging 置 1，卡号用免费标识，桩可以在没有平台时开始这次充电。配成 0 就是不做这件事。这次充电的开始、电量、结束，仍然按上面的办法记进 Flash。
